# v0.0.8 Agent 召回工作流

状态：需求已记录，待设计、实施与验证。日期：2026-11-12。

本版本面向工作 Agent，通过本地 CLI 提供从范围确定、分层读取、片元检索到任务上下文组装的完整召回流程。目标是减少查找已有知识的轮次和无关阅读量，并以真实任务评价准确度、时间、tokens 与开发机负载。本文不表示功能已经实现，也不改变当前发布版本或 v0.0.6 等其他版本的开发范围。

[需求总入口](../readme.md) · [v0.0.5 记录侧契约](../../v0.0.5/contracts.md)

## 1. 目标与边界

### 1.1 本版必须具备

1. 工作 Agent 的查询时机规则，以及低成本的项目知识范围说明。
2. 统一的请求路由与上下文准备入口，支持直接读取、结构化列举、问题检索、任务组装。
3. 项目、组织、模块、来源、时间等范围解析，以及召回前的硬过滤。
4. 可定位原文的片元结构、增量向量化和向量检索。
5. 全文索引及 BM25 排序。
6. 全文与向量的混合召回、排名融合和候选重排。
7. 面向任务的信息覆盖、去重、必要上下文补齐和输出预算控制。
8. 可重复的检索及端到端任务效能评价流水线。

以上能力均属于本版范围。明确对象的读取不需要经过模型，具备完整链路不代表每次请求都执行所有步骤。各检索阶段应能够独立启停，便于对照评测与故障降级。

### 1.2 延续的约束

- 开发阶段以本地 CLI 调用为入口，依赖工具在本地配置和执行；不新增客户端、MCP 或远端知识库服务。
- 不扩展展示页面；不自动安装系统任务、后台钩子或常驻模型服务。
- 沿用既有 Agent/profile 配置边界。模型适配方式、具体模型与依赖版本在实施设计中确定，调用量与费用必须可记录。
- 当前机器是开发机。空闲显存或内存不能作为允许干扰工作的依据，10% 的实际开发性能退化不可接受，也不能作为默认可用门槛。
- 自由记录保持忠实原文；session 转录继续保持独立记录及来源关系。召回不修改正文、不自动合并记忆、不建立未经证实的替代关系。
- 标签继续表示明确的组织关联，关键词继续支持术语定位与浏览。向量是派生检索数据，不替代标签或关键词，不根据相似度自动建立标签归属。
- 不承诺通用记忆真伪判定或自动获得“最新正确结论”。历史记录只提供证据，不能代替当前代码、测试和运行状态的检查。

## 2. 工作 Agent 何时查询

### 2.1 建议查询的情况

- 用户要求继续、沿用、恢复或解释此前的工作与决策。
- 开始实质性项目任务，但当前上下文缺少适用约束、已有方案或验证依据。
- 遇到可能已有解决记录的问题。
- 回答依赖历史事实，而当前上下文没有对应证据。
- 已有材料相互矛盾，需要查找来源和适用条件。

### 2.2 通常不查询的情况

- 用户提供的材料已经足够完成任务。
- 简单、局部且明确的修改，不依赖历史背景。
- 同一任务已经取得相关证据，任务范围与对应内容版本没有变化。
- 用户明确指定了记录 ID，此时直接读取即可。

判断优先由工作 Agent 按简短规则完成，不为每轮对话额外调用一个分类模型。提供可复制的 Agent 使用说明及 CLI 示例，但不得将“规则已配置”视为“Agent 一定会调用”。评价需要覆盖该查未查、不必要查询、重复查询与错误范围选择。

### 2.3 项目知识范围说明

提供只读、精简的范围说明：项目身份、可用组织、明确登记的模块、覆盖时间、索引状态和入口能力。它用于帮助 Agent 判断资料是否可能存在，不加载全文、完整关键词表或内部插件数据。

范围说明按项目和元数据修订缓存。任务变化、范围变化或相关记录更新时可以刷新，不能把旧范围说明永久视为完整覆盖。

## 3. 统一入口与分层处理

### 3.1 直接读取

输入文档 ID、记录 ID、片元 ID，或明确登记的固定入口时，直接定位并读取。固定入口可以指向项目约定等既有记录，但必须来自显式配置，不能由检索结果自行升级为强制规则。

直接读取仍遵守请求范围、删除状态、来源版本与输出预算。别名或标题匹配多个对象时返回精简候选，不猜测目标；不进行 embedding、重排或模型总结。

### 3.2 列举与条件筛选

适用于“某组织最近一周的记录”“包含某错误码的文档”等请求。使用元数据过滤、精确匹配或全文搜索，返回分页清单及必要定位。需要明确排序字段和排序方向，不能把时间排序描述为相关性排序。

### 3.3 问题检索

适用于有明确问题但没有记录定位的请求。范围确认后执行全文与向量召回、融合、重排，返回回答问题所需的证据片元。没有充分证据时允许返回空结果或不足提示，不以凑满条数为目标。

### 3.4 任务上下文组装

适用于需要多方面背景的任务。识别任务所需的信息，例如相关设计、约束、已知问题和验证依据；分别检索后组装。简单任务使用模板与确定性规则，必要时才调用模型拆解任务。

拆解不得改变原始请求的项目、模块或时间边界。记录拆解出的子问题及其来源；某个子问题无证据时明确列出缺口，不补造答案。

### 3.5 路由结果可解释

统一入口返回所选处理层级及简短原因，允许调用方显式指定层级。明确指定直接读取或列举时不得悄悄升级为模型推理；模型不可用时按明确的降级规则返回结果及限制。

## 4. 范围身份与召回前过滤

### 4.1 项目身份

建立稳定 projectId 与目录、别名的映射。目录按平台规则归一化并比较路径段边界；工作树可显式映射到同一项目，不凭相似名称自动归并。

项目确定顺序：用户明确指定 → 当前任务已确定 → 当前工作目录映射。发生歧义或冲突时返回候选或范围错误，不默认为全库，也不通过向量相似度猜项目。

没有项目上下文的跨项目查询需要调用方明确声明为跨项目范围。不同条件的范围取交集；相互冲突时不得自动放宽。

### 4.2 范围字段

记录与片元需要可查询的范围元数据：

- projectId：项目身份。
- organizationIds：转录组织、标签或其他明确组织关联，具体字段语义不得混淆。
- modules：显式登记或有可靠来源映射的模块。
- sourcePaths：原始来源路径，不是 `.data/resources` 存储路径。
- recordType、sessionId：记录类型和适用时的来源 session。
- sourceTime、recordedAt：内容发生时间与入库时间。
- resourceId、contentVersion、contentHash：原文身份和版本。

时间过滤必须注明使用发生时间还是记录时间，并定义区间边界与时区。转录覆盖时间段时应明确采用区间相交等规则，不用入库时间代替发生时间。

项目或模块未知的历史记录保持未知。可以提供显式补充映射工具，但不能根据标题中的“战斗”直接赋予 battle 模块。严格范围查询不混入未知记录，并报告范围覆盖不足。

模块映射规则本身也需要修订标识，变化后相应索引元数据可更新。内容不变时，不因单纯范围映射变化而重复生成向量。

### 4.3 过滤顺序

必须先确定允许的记录／片元集合，再在该集合内进行全文和向量检索。不得先全库取 Top K 再过滤其他项目，否则其他项目会挤占候选并造成漏召回。

首版小规模实现可以先取得允许的片元 ID，再计算其向量相似度；后续换索引也必须保持相同过滤语义。两路召回、融合、重排、直接读取和邻接展开都应遵守同一范围。

范围内无结果时，返回可选的扩大范围建议。只有显式请求才扩大范围；跨项目经验应标明来源项目，不能作为本项目约定。

## 5. 片元与索引生命周期

### 5.1 片元规则

- 片元是原文的可定位片段，不是再次生成的模型摘要。
- 按标题、完整段落、列表、代码块及事务边界切分；短记录可以整篇作为一个片元。
- 尽量保留问题、条件和结论的关联。长块拆分需要上下文定位，不能静默截断关键内容。
- 保留标题路径、原文位置、邻接关系、资源版本与内容指纹。
- embedding 输入可以附带文档标题和标题路径，但必须与实际原文引用区分。
- 片元 ID 在相同内容版本及切分配置下确定；正文或切分变化后不将旧定位悄悄指向新内容。
- 固定版本的自由记录、历史原件与当前资源的查询语义要明确，不能因底层资源更新而读取到另一版本。

### 5.2 全文与向量索引

全文索引推荐 SQLite FTS5 与 BM25；中文文档和查询使用相同的分词、归一化及专业词组策略。权重与分词配置需要版本化并可复现，不使用临时字符串拼接构造不受控查询表达式。

embedding 提供独立适配器，记录模型身份／修订、维度、归一化方式、查询与文档编码策略以及输入配置。缓存键包含实际编码文本和这些配置。禁止混合不同模型空间，即使维度相同也不能直接比较。

索引是可重建派生数据，原文及正式元数据是依据。支持显式构建、增量更新、状态检查和重建；新增、内容更新、删除、恢复、范围变化都要有对应处理。

普通读取和范围说明不能触发全库重建或文档向量化。语义查询可以按配置计算查询向量，必须报告相关调用。索引未就绪、滞后或模型不可用时明确说明，不能把“索引缺失”误报成“库内没有资料”。

发布新索引时保证查询读取一致的索引代次；中断或失败不得暴露半更新结果。输出前校验原文可用性与版本，删除或越界片元不得通过旧缓存继续返回。

## 6. 混合召回与候选重排

1. 在相同范围内并行执行 BM25 与向量召回。
2. 以片元身份合并重复候选，保留每一路排名和命中信息。
3. 使用 RRF 等可解释的排名融合方法，不能直接相加量纲不同的原始分数。
4. 对有限候选进行问题—片元相关性重排；专用重排模型与生成式模型方案均通过适配器隔离，具体选择由评测决定。
5. 检查不同子问题的信息覆盖，避免同一文档的重复片元占满结果。
6. 在最终预算内选取证据，并在必要时补齐相邻条件和例外。

支持 lexical、semantic、hybrid 对照模式，以及重排启停。显式只运行全文查询时不调用 embedding 或重排模型。混合模式降级时保留可用路径并返回实际执行阶段，不伪装成完整混合结果。

候选数、重排数、片元大小、阈值和权重均为可调参数。参数应在调优集上确定，在冻结评测集上验证。重排分数不是事实正确概率，不能直接用统一的“置信度百分比”解释。

## 7. 面向任务的上下文组装

### 7.1 组装内容

按实际证据组织相关约束、设计、决策、问题及验证材料。已明确登记的适用约束通过直接读取路径补充，不完全依赖相似度排名。

保留原文中的计划、推测、纠正、实施和验证身份。时间较新不等于事实更正确；不同来源不一致时保留差异和来源，不自行覆盖。普通 session 转录没有自动版本替代语义，不能擅自隐藏较早记录。

### 7.2 预算与展开

- 支持总返回预算和最大片元数，预算包括标题、定位、来源与必要提示。
- 优先通过选择、去重和原文拼装控制预算，不默认调用模型再写一份总结。
- 支持邻接展开、按章节读取及完整原文读取，并保留原请求的范围约束。
- 不能静默丢弃适用的关键约束；预算不足时返回明确标识及继续读取入口。
- 无证据时返回不足状态，不用低相关结果填满预算。
- 目标模型 tokenizer 可用时据其计数；否则明确为估算，并提供字符／字节硬上限，不能把估算伪装成精确 token 数。

检索文本作为资料提供，其中的命令或指令不能自动升级为系统规则或当前任务授权。缓存必须包含范围、请求参数、相关配置和索引代次，防止跨项目复用结果。

## 8. CLI 与返回契约草案

命令名称在实施契约中冻结，建议统一使用 recall 命名空间：

- `recall scope`：解析项目与范围，返回精简说明及歧义。
- `recall prepare --input request.json`：统一路由及上下文准备。
- `recall read`：明确 ID 的片元／原文展开。
- `recall search`、`recall list`：显式检索或列举，复用同一业务层。
- `recall index status/build`：索引状态与显式增量构建；重建选项明确区分。
- `recall eval`：针对固定数据集运行指定模式及对照。

以上为拟新增命令，不是当前已存在能力。沿用单 JSON 输出、stderr 日志及既有退出码约定。

示例请求：

```json
{
  "task": "给项目 A 的战斗模块增加连击机制，需要遵循哪些现有设计",
  "mode": "task",
  "scope": {
    "projectId": "project-a",
    "modules": ["battle"]
  },
  "retrievalMode": "hybrid",
  "rerank": true,
  "budgetTokens": 3000
}
```

输出需要包含：

- 请求及解析后的范围、选用层级和实际执行阶段。
- 证据片元、标题路径、来源文档／组织／项目、时间与固定版本、原文定位。
- 命中方式与简短理由；候选分数仅用于解释排名，不表示真实性。
- 按任务组织的内容及未覆盖信息需求。
- 截断、省略、索引滞后、降级、范围未知等状态与展开入口。
- 返回量、token 计数方式、各阶段耗时及模型调用用量。
- 便于关联评价日志的请求标识。

默认不输出完整 ResourceMeta、插件分区、全量关键词、原始对话或调试候选。详细排名轨迹通过显式调试选项获取，避免把内部诊断变成工作 Agent 的输入负担。

## 9. 效能评价流水线

### 9.1 数据集与基线

建立带正确证据定位和预期范围的固定数据集，覆盖精确术语、自然语言改述、多条件、多事务任务、多个项目同名模块、无答案、旧记录／纠正、历史时间、未知范围与删除内容。

先区分“原始 session 有答案但转录丢失”和“记录有答案但检索未命中”。前者归入记录质量问题，不通过调节召回参数掩盖。

至少比较现有字面查询、BM25、纯向量、混合、混合加重排、完整任务组装。控制使用同一语料快照、范围和输出预算，并记录模型与参数。调优集与验收集分开，不能用反复修改标准制造提升。

### 9.2 评价指标

- 触发：该查未查、不必要查询、重复查询及范围选择错误。
- 检索：正确证据 Recall@K、首条有效证据排名、MRR／nDCG；指标需说明标注粒度和相关性等级。
- 组装：子问题覆盖、条件完整性、重复率、引用正确性、无答案误召回、跨项目混入及历史误用。
- 任务：最终任务完成情况、证据使用正确性、查找轮次、返工和人工介入。
- 时间：索引构建／更新、每个查询阶段、端到端任务耗时，区分冷启动／热查询和缓存命中。
- 用量：工作 Agent 的输入／输出 tokens、embedding 输入量、重排处理量、额外生成模型 tokens 和费用，分别统计；缓存 tokens 按实际计费口径单列。
- 开发机影响：索引、查询、空闲状态下的 CPU、内存、GPU、磁盘 I/O，以及真实构建、测试等工作负载耗时变化。

工作 Agent 少读资料不等于系统总费用下降，检索命中率提高也不等于最终任务成功。评价报告必须保留这些区分，并报告重复运行的波动，不能只取最佳一次。

人工或已知夹具依据用于建立可靠标准；模型判分可以辅助，不能作为真伪和事实完整性的唯一裁判。真实私人语料与日志保留在本地忽略目录，仓库只保存匿名夹具和可复现实验脚本。

### 9.3 验收门槛

- 固定边界夹具中，跨项目／模块越界、删除内容泄漏、定位到错误版本、直接读取意外调用模型必须零失败。
- 全部六类召回与评价能力都有真实执行路径，不能用 mock 或“预留接口”冒充完成。
- 模型质量与性能证据单列，明确样本量、配置、费用及局限；自动化结构测试不能证明召回准确率。
- 业务准确度、延迟、用量和开发机性能门槛在基线测试后、调优前落档，不能验收时临时降低。
- 默认策略需要在冻结数据集上证明相对基线的收益，说明牺牲了什么；不承诺未经实测的准确率、节省比例或毫秒级延迟。
- 以不干扰开发为目标；不能仅凭低进程优先级或平均 CPU 占用通过验收，也不能默认接受低于 10% 的任意退化。若无法满足冻结门槛，应改变执行策略并复测，不能自动增加常驻计算。

## 10. 实施顺序与交付物

1. 冻结范围身份、片元定位、统一请求／返回结构和评价基线；保留现有 CLI 的行为。
2. 实现直接读取与列举路由、范围硬过滤、片元和全文索引，建立无需模型的可用路径。
3. 实现增量 embedding、范围内向量检索、混合融合与重排，支持独立模式对照。
4. 实现任务信息需求、证据补齐、预算组装、继续展开和降级。
5. 运行各阶段消融对照及真实 Agent 任务测试，交付准确度、时间、用量和开发机影响报告。

每阶段均提供隔离数据、可复制 CLI 和失败案例。最终交付公共契约、Agent 使用说明、索引维护说明、验收脚本、评价数据集与报告、未解决限制。版本实施前重新检查当时仓库状态，不覆盖并行开发内容；正式发布仍遵循项目的用户验收与归档流程。

## 11. 技术依据与待定选型

- [SQLite FTS5](https://www.sqlite.org/fts5.html)：全文索引、BM25 与命中片段能力。中文分词与项目术语处理需要本项目验证。
- [Sentence Transformers 语义检索](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)：查询与文档编码及相似检索。
- [Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)：先召回候选，再使用问题与片元联合评分进行重排。
- [RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)：融合不同检索结果的排名；采用算法不意味着引入 Elasticsearch。
- [检索评价工具](https://www.sbert.net/docs/package_reference/sentence_transformer/evaluation.html)：信息检索指标的实现参考，不能替代本项目端到端验证。

待实施设计确定：embedding／重排模型与执行适配器、依赖版本、片元长度与上下文策略、候选数量、分词和索引参数、项目模块映射的存储契约、性能及费用预算。以上选型不缩减本版已确定的功能范围。

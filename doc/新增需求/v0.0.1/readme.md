# v0.0.1 Agent 知识库初步需求

状态：已完成。用户于2026-11-11确认完成0.0.1版本并推送；当前实际能力、运行、契约及局限已归档到 [已发布v0.0.1](../../v0.0.1/readme.md)。下文保留原始需求及讨论历史，未落实的可选能力不因归档而成为已实现功能。

## 1. 定位与边界

- 独立仓库：https://github.com/trainee315/knowledge-base。
- 本地目录：`D:/project/knowledge-base`。
- 由用户日常使用的工作 Agent（Codex）主导记录、组织、检索和维护知识，重点服务日常资源收集与经验复用。
- 独立于个人项目中心的笔记模块，不依赖或沿用其业务实现。
- 本项目 CLI 接入个人项目中心（PPC），工作 Agent 通过 PPC 调用知识库能力整理笔记；知识库的业务实现和文件数据仍由本项目管理。
- 首期采用单人单机、文件持久化、CLI 统一管理和单写入者的运行边界。
- 首期完成导入、整理、查找、预览的使用流程；OCR、复杂文档解析和向量检索留待后续。
- 项目会话上下文接续不在本知识库的当前目标范围内。
- 当前对话暂时代管初步需求确定，后续切换到本仓库开发。
- 需求推进方式参考个人项目中心：版本化新增需求、实现与验证、用户验收、已发布版本归档。

### 1.1 已确认技术选型

- 运行时采用 Node.js 24 LTS，CLI 与页面使用 TypeScript，正式运行使用构建后的 JavaScript。
- 页面采用 Vue 3 + TypeScript + Vite；首期使用普通 CSS，组件库后续按需要选定。
- 使用 npm 管理依赖并提交依赖锁文件。
- 普通 CLI 命令处理完成后退出；预览按需启动本地 Node HTTP 服务，通过 `127.0.0.1` 提供页面和只读数据接口，停止预览后服务退出。
- 开发时使用 Vite 开发服务，日常预览使用构建后的页面。

### 1.2 已确认设计原则

- 核心保持简单，负责资源、meta、组织以及插件管理。
- 关键词、标签、关键词—标签关系、整理、定时任务等作为插件提供。
- 插件允许单向依赖其它插件，但必须显式声明依赖了哪些插件；不允许循环依赖。
- 核心在载入插件前先收集依赖声明、形成完整依赖关系并确定顺序，再按被依赖插件优先的顺序载入和更新数据。
- 插件管理属于核心职责；核心统一管理依赖与执行顺序，各插件负责自己的业务逻辑和具体数据更新。
- 插件化改变能力的组织方式，不取消此前已确认的首期功能、持久化约束和验收场景。
- 核心通用组织模型、meta 扩展方式、插件声明格式、加载与更新生命周期的具体协议见设计草案，仍待讨论。

## 2. 资源与元数据

- 支持所有类型的文件作为资源入库，Markdown 文件也作为资源。
- 资源库内按照文件类型分类存放。
- 资源文件使用 UUID 命名；具体扩展名、类型识别与无扩展名处理规则待细化。
- 资源目录同级放置元数据库；每个资源对应一个同名、后缀为 `.meta` 的元数据文件。
- 元数据采用分层结构，包含共用数据，以及按资源适用的纹理数据、PNG 数据、标签数据、关键词数据等。
- `.meta` 采用 JSON，带 `schemaVersion`，通过迁移命令升级；具体字段和迁移协议在实现设计时细化。
- 首期正文解析支持 Markdown、TXT、JSON；其它格式保存原件、基本信息和文件名关键词，并标记正文未解析。
- UUID 表示稳定的资源身份。显式更新内容保留 UUID、增加内容版本并保留旧内容；普通导入按新资源处理，但先执行重复检测。
- 使用内容哈希识别完全相同的文件，重复导入默认返回已有资源，允许显式创建独立副本；文件名相同不作为重复依据。
- 删除默认进入可恢复的回收状态，保留引用和恢复能力；彻底清理由显式命令完成。
- 组织和 Markdown 内部资源引用使用 UUID，由管理器解析实际文件路径。

## 3. 组织层

组织数据放在资源库外部，支持：

- 标签：确定匹配的组织方式。
- 关键词：模糊匹配的组织方式。
- 体系化结构：成体系、成系列的文档组织。
- 其它可扩展的组织方式。

工作 Agent（Codex）通过 PPC 调用本项目 CLI，以脚本管理数据。体系在人为指导下生成；标签、关键词组织自动生成。关联整理 Agent 提供关键词与标签的关联程度，工作 Agent 负责结合资源判断归属。精确匹配、模糊匹配及归属判断的接口语义在设计阶段进一步细化。

### 3.1 查询与匹配

- 查询支持文件名、正文、关键词、标签和体系归属。
- 标签采用确定匹配；关键词首期采用归一化后的包含匹配。
- 不同筛选条件取交集，同一条件内多个值默认取并集。
- 查询结果显示匹配原因和解析状态；归一化细节、排序和分页在技术设计时细化。

### 3.2 数据权威来源

- 资源 `.meta` 保存资源基本信息、提取关键词、确定的标签归属，以及归属判断的来源和依据。
- 外部组织目录保存标签定义、别名、关键词—标签评分、体系节点及排序；体系节点通过 UUID 引用资源。
- 资源与标签的关联不在资源侧和组织侧分别维护两份独立记录。标签和关键词的反向索引可从正式数据重建。
- 拒绝关联的结果同样保存；具体字段与接受结果一起在元数据设计时确定。
- 人工修正明确记录来源，优先于自动结果；人工确认或拒绝持续有效，自动整理只能提出复核建议。

### 3.3 组织方式扩展

- 首期提供标签、关键词、体系三种组织方式，统一提供标识、定义、资源关联、查询和预览能力；标签与关键词按插件实现，体系与通用组织核心的具体边界继续讨论。
- 组织方式管理负责注册、配置、启停等生命周期；全新算法或专属页面通过增加处理器代码实现。
- 删除正在使用的组织方式前，需要先迁移或清理其关联。

## 4. 关键词与标签的关联

确定的分层链路：

资源 → 脚本生成关键词 → 关联整理 Agent 提供关键词—标签关联程度 → 候选资源 → 工作 Agent（Codex）判断标签归属。

- 关键词由脚本自动生成。
- 关联整理 Agent 负责给出关键词与已有标签之间的关联程度，管理器负责保存和使用评分结果。
- 新增标签时，通过关键词评分找到可能相关的历史资源，再由工作 Agent（Codex）判断是否归入标签。
- 评分用于候选发现，资源是否归属标签需要后续判断。
- 评分公式、阈值、关键词选择与更新算法后续再定。

## 5. Agent 角色、模型与运行方式

### 5.1 工作 Agent

- 指用户日常使用的 Codex，负责理解整理要求、记录和组织笔记、检索资源，以及判断资源的标签归属。
- 本项目 CLI 接入 PPC 后，由 Codex 通过 PPC 使用这些能力。
- 此角色沿用用户已有的工作 Agent；本项目不因该角色而新增一个必须独立部署的归属判断 Agent。

### 5.2 标签—关键词关联整理 Agent

- 专门给出标签与关键词之间的关联程度，为候选资源发现提供依据。
- 不限定使用哪种模型、服务或实现，只要能提供所需关联程度即可。
- DeepSeek 是此前提出的实现选项，不再作为必须依赖。
- 关联程度不直接代表资源的最终标签归属；最终归属仍由工作 Agent 判断。

### 5.3 运行方式

- 导入、内容更新、标签新增和标签定义修改产生任务；事件处理与每晚自动整理使用同一套任务队列，夜间补齐积压、失败任务和历史资源整理。
- 每个任务记录输入版本、处理器版本和状态；相同输入不重复执行，相关输入变化后重新计算。
- 提交结果时检查输入版本，防止旧任务结果覆盖新数据；关联拒绝结果在相关内容或标签定义变化前不重复判断，人工决定遵循第 3.2 节。
- 模型调用设置可配置的次数、费用预算、超时和重试上限；达到上限后保存进度，留待后续继续。
- 工作 Agent 通过结构化接口读取候选和材料、提交判断，由管理器校验并保存，不直接修改业务文件。
- 夜间是否自动唤起工作 Agent，以及调度归属、具体时间和默认预算，仍待确定；双 Agent 分工优先于此前独立归属判断执行器的建议。
- 不在本阶段创建真实定时任务或发起模型付费调用。

## 6. 仓库管理器

- 根目录提供 `./cli.bat`，作为脚手架/统一命令入口。
- `./src` 为仓库管理器实现入口。
- 至少提供资源增删改查、组织增删改查、组织方式增删改查。
- 核心统一管理插件及其声明的依赖，先形成依赖关系，再按顺序载入和更新插件数据。
- 资源与组织的关联管理应纳入管理器能力，具体命令、参数与输出格式待定。
- CLI 接入 PPC，供工作 Agent（Codex）通过 PPC 调用管理器维护数据；接入命令、参数传递和结果格式待定。
- 关联整理 Agent 的结果由管理器接收和保存，其具体实现不改变工作 Agent 的调用入口。
- CLI 提供稳定的 `--json` 输出和错误码；数据目录可通过 `--data-dir` 指定，支持数据与管理器代码独立存放和升级。
- 提取器、评分实现、组织处理器与预览通过独立接口接入；具体接口在技术设计时确定。

## 7. 临时页面预览

通过只读的临时页面服务提供：

- Markdown 简单渲染。
- 资源基本信息及资源引用预览。
- 组织数据的简单预览。

页面按第 1.1 节的已确认选型实现；具体启动停止命令、UUID 引用解析协议及插件页面的扩展方式，在技术架构讨论中确定。

## 8. 持久化约束

- 暂不依赖服务器、数据库等组件保留持久化业务状态。
- 资源、元数据和组织数据以仓库文件保存。
- 配置允许单独管理，例如关联整理 Agent 所使用的模型或服务配置。
- 临时页面服务用于预览；不作为独立的持久化状态来源。
- 所有写操作经过管理器；同一数据目录同时只允许一个写入进程，预览和查询可以并行读取。
- 单文件采用临时文件写入后替换；涉及多个文件的操作记录操作日志，启动时恢复未完成操作。可重建索引不作为数据恢复依据。
- 明确区分原件、正式元数据、组织数据、任务状态、派生结果和缓存；任务进度应能持久化并用于恢复，可重建索引和缓存可删除重建。
- 密钥单独配置，不进入资源库和 Git；首期提供正式数据的备份和恢复能力。

## 9. 待细化的验收方向

以下行为纳入首期验收，具体测试数据和量化标准在技术设计时补充：

1. 多种格式文件能够入库，按类型保存并获得 UUID；资源与 `.meta` 一一对应。
2. 可通过 `cli.bat` 完成资源、组织及组织方式的增删改查，并在接入 PPC 后供工作 Agent（Codex）通过 PPC 使用。
3. 脚本能够生成关键词；关联整理 Agent 能提供标签—关键词关联程度，用于召回历史候选资源，再记录工作 Agent（Codex）的归属判断。
4. 事件触发与夜间整理能够按后续确定的任务范围推进处理流程，具体失败与恢复标准待补充。
5. 临时页面能够渲染 Markdown 并预览组织。
6. 关闭临时页面服务及管理器后，持久化内容仍保存在文件中，不依赖数据库。
7. 体系化结构的生成符合人为指导，标签和关键词组织按约定自动维护。
8. 重复导入返回已有资源，显式内容更新后 UUID 和内部引用保持有效，旧内容能够保留。
9. 人工拒绝不被自动整理覆盖；标签定义变化后能重新整理受影响的自动判断。
10. 删除后能够恢复；多文件操作和处理任务中断后能够恢复或继续，旧任务不得覆盖新数据。
11. 索引删除后能够重建，正式数据能够备份和恢复。
12. 查询遵循筛选组合规则并显示匹配原因；不支持正文解析的资源仍可入库和查询，并能识别其解析状态。
13. 插件依赖必须显式声明；载入前能够形成依赖关系并检测循环，加载和数据更新均遵循被依赖插件优先的顺序。

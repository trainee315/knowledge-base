## 已确认运行时与页面方式

- Node.js 24 LTS + TypeScript，构建后由 Node 运行 JavaScript。
- Vue 3 + TypeScript + Vite，首期普通 CSS；npm 管理依赖并提交锁文件。
- 普通命令按需执行后退出。预览时启动本地 Node HTTP 服务，通过 `127.0.0.1` 提供构建后的页面和只读接口，停止预览后退出。
- 开发环境使用 Vite 开发服务，日常预览使用构建产物。

已确认支持通过 `--data-dir` 将数据与管理器代码分开存放。目录结构在核心与插件边界确定后细化，具体默认位置和 Git 跟踪范围待定。

## 核心与插件边界建议

核心管理资源、meta、组织与插件；插件显式声明单向依赖，核心先形成依赖关系再按顺序载入和更新数据。这些原则已确认，本节对具体机制的细化仍属设计建议。

### 核心管理通用数据与插件

- 资源：身份、内容与历史版本、哈希、导入更新、回收恢复和基础查询。
- meta：共用信息、扩展数据、版本检查与受控更新。
- 组织：组织实例的身份、类型、名称及通用引用管理，不内置标签匹配、关键词提取、关系评分或整理策略。
- 插件：声明收集、依赖校验、顺序计算、加载与数据更新的统一协调。
- 文件写入、单写入者约束、操作日志、恢复与引用校验作为以上能力的基础设施，由核心统一保证。

插件运行宿主属于核心的插件管理能力，负责加载、命令和能力注册、运行上下文，以及依赖顺序控制。持久化业务任务队列、模型预算、整理算法和定时策略仍由插件实现；核心协调插件执行，不解释这些业务含义。

### 依赖关系、加载与数据更新

用户要求在加载前形成依赖树。考虑到多个插件可能共用一个依赖，建议内部采用有向无环图（DAG），对外可展示依赖树。若 A 声明依赖 B，则 B 必须先于 A 加载和完成相应数据更新；共享依赖在同一轮执行中只处理一次。

建议采用以下流程：

1. 读取静态插件声明，收集插件标识、版本、直接依赖以及兼容性要求；此时不执行插件入口或数据更新逻辑。
2. 核心构建本次启用插件及其依赖的完整关系，检查重复标识、缺失或停用的依赖、自依赖、循环依赖及版本兼容性。
3. 校验通过后生成稳定的依赖优先执行顺序；没有先后约束的插件采用固定排序，首期串行执行。
4. 依次加载插件、执行必要的数据初始化或结构迁移，再标记为就绪。依赖尚未就绪时，不进入依赖方的初始化。
5. 业务数据需要刷新时，由核心确定受影响的插件范围，同样按依赖优先顺序调用更新逻辑。依赖数据完成本轮更新后，依赖方才能消费对应版本的数据。

建议将数据结构迁移和日常业务数据刷新分开：迁移在数据版本不兼容时执行；关键词提取、评分或整理等刷新由变化或显式任务触发，不因每次启动而无条件全量执行。具体哪些变化触发哪些插件、如何记录输入版本与本轮进度，在后续协议中确定。

依赖声明用于实际能力访问校验，插件不能借由全局查找或读取内部文件使用未声明插件。插件各自声明直接依赖，核心计算传递依赖；依赖范围与版本匹配规则待细化。

建议依赖校验失败时不开始本轮插件激活和数据修改，并报告缺失项或完整循环路径。加载或数据更新中途失败时，阻止受影响的依赖方继续执行并保留失败状态和恢复进度；不把部分完成描述为整轮完成，也不承诺整批插件自动回滚。独立分支是否继续执行由后续失败策略确定。

### meta 扩展与引用

建议将 meta 分为共用字段和按插件标识分区的扩展数据，各插件独立记录数据版本并迁移自己的分区。核心只校验通用结构、版本冲突和引用有效性；未知或已停用插件的数据应原样保留。

资源与组织的引用采用核心可识别的统一结构，具体标签语义、权重、判断来源等由插件解释。资源关键词和最终标签归属仍以资源 meta 为权威记录；外部组织目录保存定义、评分和体系结构，反向索引可以重建。不能因拆分插件而再增加一份独立的最终归属记录。

插件需要的评分、任务和缓存文件通过管理器提供的受控存储入口保存，声明所属插件和正式数据/缓存类别，并纳入统一备份、恢复与写入约束。插件不直接改写其它插件的分区。

### 插件协作

建议首期交付随工程构建的本地 TypeScript 插件，通过配置启停。所有跨插件依赖必须声明，由核心按前述流程校验和排序；具体标识、版本、依赖和能力声明格式待定。插件 API 版本与各插件数据版本分开管理。

- 标签插件负责标签定义、别名、确定匹配，以及接收和保存工作 Agent 的归属判断；关键词插件负责提取、归一化和关键词查询。
- 关键词—标签关系插件依赖前两者的公开能力，调用可替换评分实现并提供关联程度。
- 整理插件组合内容处理、关键词、评分和候选查询，向工作 Agent 提供待整理结果并接收其判断。
- 建议通用任务执行也作为插件提供，供整理和定时插件复用持久化队列、去重与重试能力。
- 定时插件只决定何时触发任务，具体资源处理交给相应插件；夜间是否唤起工作 Agent 仍待确定。
- 建议体系化组织、内容提取和专用预览也通过插件扩展；组织核心保留通用对象与引用能力。

插件之间通过公开能力和显式依赖协作，不读取对方内部文件。基础数据变化在提交后提供事件通知；核心保持依赖优先的数据更新顺序，任务插件提供业务任务的排队、去重和重试。任务插件结合可持久化的变化记录或版本检查补齐漏处理，不能仅依赖进程内事件实现夜间恢复。核心写入失败与后续插件处理失败分别报告，插件失败不会把已成功入库的资源描述为未入库。

### 插件停用与界面

建议核心按加载顺序的逆序停用插件，先停用依赖方，再停用被依赖方。停用保留其正式数据，隐藏相应能力并明确报告不可用。存在依赖时阻止单独停用，或通过显式操作一并停用依赖方；卸载代码与清理数据分开操作。

基础页面提供资源、meta 和通用组织浏览。插件可以增加自己的信息面板、查询条件或组织预览；首期插件页面随 Vue 应用一起构建，运行时按启用状态展示。新增插件允许重新构建，暂不引入热加载或远程插件分发。

建议验证以下边界：关闭业务插件后仍可进行资源与通用组织的基本管理；增加一种组织插件时，无需修改核心来识别新的业务类型；共享依赖每轮只处理一次；依赖循环在插件运行前被发现；前置插件更新失败时，其依赖方不能读取该轮未完成数据继续更新。

## 两类 Agent 与 PPC 接入

已确认的角色分工见 [需求文档第 5 节](./readme.md#5-agent-角色模型与运行方式)：工作 Agent 是用户日常使用的 Codex，通过 PPC 调用本项目 CLI 整理笔记；关联整理 Agent 仅提供标签—关键词关联程度，实现方式不限。

建议将调用关系设计为：

```text
用户 → 工作 Agent（Codex）→ PPC → 本项目 CLI → 管理器 → 知识库文件
管理器 → 关联整理 Agent → 关联程度 → 管理器保存评分并提供候选查询
```

PPC 承担调用入口与命令转发，本项目管理器保留知识库业务逻辑与数据管理职责。工作 Agent 通过同一入口查询候选、读取资源、提交归属判断，不要求在知识库内实现独立的 Codex 运行时。

建议关联整理 Agent 使用可替换的评分接口：输入标签定义与关键词，输出对应关联程度；评分尺度、批量格式和失败表示后续确定。该接口不要求实现完整的工具调用循环，也不承担资源的最终归属判断。

## 管理器整体职责

建议 cli.bat 只负责启动与传递参数；管理器由核心（包含插件管理与运行宿主）和插件共同提供产品能力，供 CLI、处理任务及临时预览复用。以下是管理器整体职责，不表示这些业务都进入核心。

- 资源管理：导入、查询、修改、删除资源和元数据，并协调关联数据的变化。
- 组织管理：管理具体标签、关键词或体系实例，以及实例与资源的关系。
- 组织方式管理：管理组织机制的定义、处理器及预览方式。通用处理器可复用，新增行为可能需要增加代码。
- 处理流程：内容提取、关键词生成、调用关联整理 Agent 评分、候选召回，以及接收和保存工作 Agent 的归属判断。
- 评分适配：封装可替换的关联程度接口；DeepSeek 可作为实现选项，具体模型、服务和参数可配置。
- 存储：集中处理文件写入、关联校验和异常恢复。

## 资源与元数据建议

- 使用 UUID 作为稳定引用，元数据保留原文件名和来源。
- .meta 已确定采用带 `schemaVersion` 的 JSON；建议共用字段由核心管理，内容、图片、用途、格式、标签和关键词等扩展归对应插件分区，具体字段待定。
- 图片格式与纹理用途分开描述；PNG 文件不自动等同于纹理。
- 将文件已入库与内容已解析分开记录。
- OCR、文本提取、图片描述作为派生内容保留出处。
- 工作 Agent 生成的总结和分析也可作为资源入库，并记录依据的源资源。
- 显式更新内容保留 UUID、增加内容版本并保留旧内容；完全相同内容按哈希去重，允许显式创建副本；删除默认可恢复。历史内容的目录布局和恢复命令在技术设计时细化。

## 组织与关联建议

建议区分组织方式和组织实例：标签是一种组织方式，图像压缩是具体标签；体系化结构是一种方式，某个教程系列是具体体系。

关联整理 Agent 提供的关键词—标签评分用于候选召回，工作 Agent 判断后的资源—标签关系表达最终归属。评分不得直接等同于确定归属。

已确定在资源元数据保存关键词、确定的标签关联及判断来源和依据，以可重建的组织侧反向索引支持查询。标签定义、别名、关键词—标签评分及体系节点在外部组织目录保存。体系通过 UUID 引用资源，并保存节点与顺序。

记录拒绝关联的判断、判断依据及输入版本，避免反复处理；发生相关变化后重新判断自动结果。人工决定持续有效，自动整理只能提出复核建议。

## 运行流程建议

事件触发和夜间整理共用任务队列，夜间补齐积压、失败和历史回填任务；建议由任务执行与整理插件提供这些能力。已确定记录输入版本、处理器版本和进度，支持去重、重试和断点继续，并在提交结果时检查版本。建议在此基础上记录评分实现信息，事件合并和队列文件协议待细化。

新资源：生成关键词，查询已有关系评分，必要时调用关联整理 Agent 补充评分，召回候选标签，由工作 Agent 判断归属并通过 PPC 调用 CLI 保存。

新标签：调用关联整理 Agent 从已有词表建立关系评分，召回历史候选资源，由工作 Agent 判断归属并通过 PPC 调用 CLI 保存。

标签定义或关键词信息变化：更新受影响的评分，将需要重新判断归属的候选提供给工作 Agent。

候选召回完成不代表全库完整覆盖。无法解析的资源和未检查范围应能被识别；具体覆盖策略后续确定。

建议夜间任务先处理脚本能够完成的工作与关联程度更新；等待工作 Agent 判断的资源保留为待整理候选，不将评分完成视为最终归属判断完成。夜间是否需要唤起工作 Agent，以及由 PPC 还是操作系统负责调度，均待确定，不将独立归属判断执行器作为首期既定前提。

定时任务可通过 CLI 推进处理，无需保持预览服务在线。直接修改文件后的变化检测机制待定。

## 预览与持久化建议

预览第一版已确定为只读，支持 Markdown、资源引用、资源基本信息和组织结构浏览。Vue 页面通过本地 Node 服务的只读接口访问知识库，不持有独立业务状态；插件页面的注册接口待讨论。

任务进度使用文件保存以支持恢复；提取结果和报告的具体文件形式待确定。运行时可建立内存索引。缓存可删除重建，正式数据与缓存应有明确边界。

已确定单写入者、单文件临时写入后替换、多文件操作日志及启动恢复；预览和查询可并行读取。密钥单独配置且不进入资源库和 Git。具体锁、读取一致性、恢复协议、密钥配置方式和其它文件的 Git 跟踪范围在实现方案阶段确定。
